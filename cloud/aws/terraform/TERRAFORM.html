▶ Terraform workflow commands
1. Set AWS profile (every new terminal session)
. .\cloud\aws\set-profile.ps1     # PowerShell
call cloud\aws\set-profile.bat    # CMD
2. Initialize (downloads providers, connects to S3 + DynamoDB)
terraform init
3. Preview changes (free, read-only)
terraform plan
4. Apply (creates real AWS resources — incurs costs)
terraform apply
5. Destroy (always run when done to avoid costs)
terraform destroy
6. Configure kubectl after apply
aws eks update-kubeconfig --name cicd-k8s-cluster --region eu-west-1 --profile cicd-k8s
⚠ Cost warning: EKS cluster, Fargate tasks, NAT Gateway, and Elastic IP incur charges. Always run terraform destroy when finished.

Remote State — S3 Native Locking

Centralized state storage with S3-native locking (Terraform 1.10+) — no DynamoDB required

⚠ The Problem
  • ✗ Local terraform.tfstate is per-machine — every developer has a different state
  • ✗ Two parallel terraform apply runs corrupt the state file
  • ✗ CI/CD runners have no persistent local state between runs
  • ✗ State contains sensitive data — should not be committed to git
✅ The Solution
  • ✓ State stored in S3 — one shared source of truth
  • ✓ S3 native lock file prevents concurrent runs from conflicting (no DynamoDB needed)
  • ✓ S3 versioning allows rollback to any previous state
  • ✓ Encryption at rest + public access blocked
✅ Current Approach — S3 Native Locking (Terraform 1.10+)

🔒 Terraform backend config 
backend "s3" {
  bucket       = "cicd-k8s-terraform-state"
  key          = "eks/terraform.tfstate"
  region       = "eu-west-1"
  use_lockfile = true
  encrypt      = true
}
use_lockfile = true — introduced in Terraform 1.10. Stores a .tflock file alongside the state object in S3 instead of using DynamoDB. No extra AWS service required.
Note: Variables are not allowed inside backend blocks — all values must be hardcoded.

Locking mechanism
🔒 Lock Acquired
When Terraform starts, it writes a .tflock file to S3 alongside the state object (e.g. eks/terraform.tfstate.tflock). Any other Terraform process that tries to run sees the lock file and fails with a conflict error.
🔓 Lock Released
After apply completes (or fails), Terraform deletes the .tflock object from S3, releasing the lock. If a process crashes without releasing, you can force-unlock with terraform force-unlock <LOCK_ID>.
✅ CI/CD Credentials
GitHub Actions uses AWS_ACCESS_KEY_ID + AWS_SECRET_ACCESS_KEY + AWS_DEFAULT_REGION injected as repository secrets. Local development uses AWS_PROFILE=cicd-k8s via set-profile.ps1.
🛠 Bootstrap commands (one-time setup — S3 only)
⚠ The S3 bucket must exist before running terraform init. It cannot be managed by Terraform itself (chicken-and-egg problem) — create it manually once via AWS CLI. No DynamoDB table is needed.
1. Create S3 bucket
aws s3api create-bucket \
  --bucket cicd-k8s-terraform-state \
  --region eu-west-1 \
  --create-bucket-configuration LocationConstraint=eu-west-1 \
  --profile cicd-k8s
2. Enable versioning
aws s3api put-bucket-versioning \
  --bucket cicd-k8s-terraform-state \
  --versioning-configuration Status=Enabled \
  --profile cicd-k8s
3. Block all public access
aws s3api put-public-access-block \
  --bucket cicd-k8s-terraform-state \
  --public-access-block-configuration \
    "BlockPublicAcls=true,IgnorePublicAcls=true,BlockPublicPolicy=true,RestrictPublicBuckets=true" \
  --profile cicd-k8s
